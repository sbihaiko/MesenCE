# F12.5 — `<addition>` from the composition editor (2026-09-19)

Scope and stop rule live in the PRD (Part A §4, Phase 12, row F12.5); the
decision is ADR-0196, §3 (the synthetic target key) and §4 (the round trip and
the lint). The stop rule: *the expanded pose renders pixel-exact on a known
frame, and the pack round-trips with the synthetic keys listed.* This log is
the evidence for both halves, on one pose of a CHR ROM game and one pose of a
CHR RAM game.

## 1. The two poses

Both are composed through the real ViewModel path — `load` → `seed_sprite` →
`add_overflow(dx, dy)` → `export` — so nothing in the measurement bypasses the
editor's own state machine.

| | Mega Man 3 (CHR ROM) | Contra (CHR RAM) |
|---|---|---|
| pose | `pose021`, 10 members, 188 frames, extent 4×3 | `pose001`, 6 members, 219 frames, extent 3×2 |
| root cell (ADR-0196 §2 = ADR-0189 §1) | node 2 | node 30 |
| root appearances | 3455 | 240 |
| anchor key as `hires.txt` spells it | `0412` / `FF0F3919` (CHR index 1042) | `007EFFFFE3E70000007E817E9D18FFFF` / `FF36160F` |
| overflow offsets tested | (16, −24) and (24, −24) | (16, −24) and (24, −24) |

The root is the pose's **most-seen** member, which is the opposite of
`pose_anchor` (ADR-0171 §5, the rarest member). One implementation judgement
was needed inside §2 and is recorded here: `pose_root` **skips members whose
recorded pattern is sixteen zero bytes**. A pose entry carries the transparent
cells of the OAM silhouette as well as the drawn ones, and on both games the
blank cell is the most-seen member of all (Contra node 0: 1356 appearances;
Mega Man 3 node 0: 12 939). Anchoring there would fire the overflow off every
blank sprite cell on screen — the same "paint the artist's overflow onto an
unrelated tile" failure ADR-0196 §3 exists to rule out, arriving through the
anchor instead of the target.

## 2. The synthetic keys, and why each is provably unmatched

| | key emitted | why no ROM tile can equal it |
|---|---|---|
| Mega Man 3 | `2000` / `0D0D0D0D` | `2000` is hex 8192, and the ROM's iNES header declares exactly 8192 CHR tiles (indices `0000`–`1FFF`). The PPU cannot fetch an index past the end of CHR, so the key is **unmatched by construction**. `mep_build --rom` makes that assertion against the header rather than trusting the sidecar; rebuilding the same pack against a 32 768-tile header is refused ("target index 2000 is inside the ROM's CHR"). |
| Contra | `00000000000000010000000000000000` / `0D0D0D0D` | `HdTileKey::operator==` compares the palette and all 16 pattern bytes together on CHR RAM, so both halves are reserved. The pattern is all-zero but for the marker row carrying ordinal 1 (byte 7); the ordinal is 1-based on purpose, because the 0th reserved pattern would be sixteen zero bytes, one of the most-recorded tiles there is. The palette is `$0D` in all four entries — "blacker than black", which no shipping game writes to a palette. |

The CHR RAM side is **evidence-bounded, not proven**, and the build performs
the check rather than assuming it: `Pack.reserved_palette_seen()` scans every
palette the recording's own vocabulary carries and refuses the whole export if
`0D0D0D0D` is among them. Both recordings report `[]`. That is evidence over
the routes these recordings covered, not over the game.

The cell that carries the key is an ordinary sheet cell, reserved blank on a
row of its own below the pose and marked `"synthetic": true` with its ordinal
and pose. The `additions[]` record points at the **cell**, never at the key:
the `<tile>` rule and the `<addition>` that targets it come out of the same
cell, so the two cannot drift apart across a rebuild.

## 3. The round trip (ADR-0196 §4)

`python3 scripts/mep_build.py build <pack> [--rom <rom>]`, then
`python3 scripts/mep_lint.py <pack>`:

| | Mega Man 3 | Contra |
|---|---|---|
| `<addition>` emitted | `<addition>0412,FF0F3919,16,-24,2000,0D0D0D0D` | `<addition>007EFFFFE3E70000007E817E9D18FFFF,FF36160F,16,-24,00000000000000010000000000000000,0D0D0D0D` |
| `<tile>` rule for the target | `<tile>35,2000,0D0D0D0D,4,112,1,N` | `<tile>36,00000000000000010000000000000000,0D0D0D0D,4,76,1,N` |
| build | exit 0 — `478 tile(s), 36 sheet(s)`; `1 <addition> line(s) from the sheets' overflow layer, 1 synthetic target key(s)` | exit 0 — `549 tile(s), 37 sheet(s)`; same info line |
| lint | **exit 0** — `0 error(s), 36 warning(s)`, info line reads `… 295 conditions, 1 additions` | **exit 0** — `0 error(s), 36 warning(s)`, `… 307 conditions, 1 additions` |

The 36 warnings are the pack's pre-existing ones (sheet geometry and unresolved
metatile placements); they are identical in the control variant, which carries
no `<addition>` at all. A rebuild of the same folder leaves exactly one
`<addition>` line: the sheets are the source of truth for the layer, and a
carried copy is dropped before the generated one is written.

`ignorePalette` is never written, and the lint refuses it outright — dropping
the palette half of a CHR RAM synthetic key is precisely what would let it
collide.

## 4. The pixel comparison

**Method.** Three variants per game, built from one unbuilt copy of the same
recorded pack and composed identically, so the only difference between them is
the `<addition>` tag:

- **A — control.** The same composed sheet, the same reserved cell, the same
  synthetic `<tile>` rule, `additions: []` in the sidecar. Its `hires.txt`
  differs from B's by exactly one inserted line.
- **B.** Overflow at (16, −24).
- **C.** Overflow at (24, −24).

The synthetic cell is painted solid magenta `#FF00FF` in the scaled sheet.
That colour appears **nowhere** in the control frame (0 magenta pixels in A),
so every magenta pixel in B or C is the overflow and nothing else.

Each variant is rendered by `scripts/headless_record <rom> 12 <out> screenshot
capture log state=stage1-run.mss input=stage1-run.txt`, i.e. the same state,
the same input and the same frame target. All three land on **frame 1924** and
all three log the same pack load, so the comparison is between frames, not
between runs. Determinism was checked rather than assumed: a duplicate of the
control (`A2`, a byte copy of A's pack) renders checksum `0x771AEBE5`, exactly
A's.

The 12 s target is not arbitrary. A duration sweep (4–60 s, control vs B) shows
the tag firing on frames 1443, 1684, 1924 and 2165 and not after, because the
input script runs dry at ~16 s and the anchor leaves the screen; a first attempt
at 20 s compared two identical frames and proved nothing.

**Result — Mega Man 3 (CHR ROM), frame 1924.**

`diff(A, B)` is **800 pixels, one connected component**, bounding box
(700, 196)–(731, 227) — a single 32 × 32 screen block, which is one 8 × 8 NES
cell at the pack's `<scale>4`. Every one of those 800 pixels is `#FF00FF` in B
and was black in A. **There is no other difference anywhere in the frame.**
`diff(A, C)` is the same 800-pixel component at (732, 196)–(763, 227), and
C's magenta set equals B's translated by exactly +32 px — 8 native pixels, the
24 − 16 the two offsets differ by. Nothing else moved.

**Result — Contra (CHR RAM), frame 1924.**

`diff(A, B)` is **1008 pixels in two components**:

1. **896 pixels**, bounding box (192, 16)–(223, 47) — the addition, one 32 × 32
   screen block, all `#FF00FF` in B and all black in A. `diff(A, C)` has the
   same component at (224, 16)–(255, 47), and C's magenta set is B's translated
   by exactly +32 px.
2. **112 pixels**, bounding box (0, 0)–(27, 3) — a 7 × 1 *native*-pixel strip in
   the screen's top-left corner that turns from black to `#155FD9`. It is
   identical in B and C, i.e. independent of the offset, and it is a Core
   defect, not this slice's output. See "Honest limits".

**Why the drawn cell is 896 and 800 pixels rather than 1024.** Sampled at
native resolution, the addition covers:

```
Mega Man 3            Contra
#.......              #.......
#.......              #######.
########              ########
########              ########
########              ########
########              ########
########              ########
########              ########
```

`HdNesPack::InsertAdditionalSprite` seeds the additional sprite into **one**
`ScreenTiles` entry — the pixel at `(sourceX + offsetX, sourceY + offsetY)` —
and the renderer expands the tile from there, so the part of the cell that
precedes the seeded pixel in scan order is not covered. The shape depends on
the anchor's sub-tile phase, not on the tag: it is byte-identical between B and
C on both games, and it is what any HD pack's `<addition>` produces today. The
claim this log makes is therefore exact and narrow: **the difference the tag
makes is precisely the synthetic target's art, at the offset asked for, and
nowhere else.**

## Honest limits

- **No human has opened the editor and done this by hand.** Every composition
  in this log was driven through `ComposeViewModel` from a script. The
  "Overflow" pane exists, is wired to the same ViewModel methods and is drawn
  by `refresh_all`, but a person adding an overflow cell with the mouse,
  reading the offset back off the listbox and exporting is a **separate panel
  row**, not something measured here.
- **A Core defect contaminates the Contra frame, and is not fixed here.**
  `HdNesPack::ProcessAdditionalSprites` binds `HdPpuPixelInfo& lineFirstPixel =
  _hdScreenInfo->ScreenTiles[0];` and then writes `lineFirstPixel =
  _hdScreenInfo->ScreenTiles[y << 8];` inside its scanline loop. C++ reference
  assignment copies the value, so every iteration overwrites the screen's
  **first pixel** with the first pixel of row `y`. The pass runs only when the
  pack declares at least one `<addition>`, which is exactly why the control
  does not show it. That is the 112-pixel artefact above; Mega Man 3 happens
  not to show it because the copied value matches. It is upstream Mesen code,
  out of scope for F12.5, and is reported for the bug board rather than patched
  in passing.
- **The CHR RAM proof is evidence-bounded.** `$0D` in all four palette entries
  is reserved by convention and checked against what these two recordings saw.
  A recording covers routes, not a game; a pack recorded elsewhere could in
  principle observe it, which is why the check is run per pack and refuses the
  export rather than being asserted once in a doc.
- **The lint's §3 check is pack-local.** A linter has no ROM, so a CHR ROM
  target is required to be past every index the pack's own manifest keys. Only
  `mep_build --rom` makes ADR-0196 §3's actual header assertion.
- **One pose per game, one overflow cell per pose.** The bounded input the PRD
  asks for. Multi-cell overflow layers are exercised only by the unit tests
  (ordinals are allocated pack-wide, so two composed sheets cannot claim one
  synthetic key), not by a rendered frame.
- **The offsets are not a designed silhouette.** (16, −24) and (24, −24) were
  chosen because they differ by one cell and land on screen; they say nothing
  about what an artist would want. The measurement is about the mechanism.
- **`additions[]` lives in the composed sheet sidecar (`usrNNN.json`).** There
  is no Python-writable pose sidecar — `poses.json` is the C++ recorder's
  output — so the overflow layer is recorded next to the cells that carry its
  art. A future slice that gives poses a writable sidecar may want to move it.
