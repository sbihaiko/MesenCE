# F12.2 — mechanical replay of the panel script (2026-09-19)

**This does not close the F12.2 human panel row, and cannot.** That row asks
whether *a person who did not build the feature* can find *Copy as MEP sheet
cell*, understand what it gave them, and paste it without ever opening
`textures/hires.txt` — a cold read, measured on a person, once. A machine
already knows where the menu item is, so every number below is produced by
something that cannot be surprised by the UI. The proof that the distinction is
real is in the script itself: steps **P5** and **P6** carry corrections dated
2026-09-18 (the tile grid is *not* drawn by default; the panel stays null until
you **click**, and the first evaluator hovered). Nothing in this log would ever
have produced those two findings.

What this log does record is the other half — the half a person should not be
spending their one cold read on. The setup steps S1–S4 are now machine-checked
preconditions, and the paste-and-paint round trip P9–P14 is replayed end to end
on both bounded games until a magenta square is asserted in a real screenshot.
The human run can still fail on discoverability; it can no longer be silently
defeated by the environment.

## P5–P8 — the headless MVVM test

`UI.HeadlessTests/CopyAsMepSheetCellTests.cs` drives the real
`TilemapViewerWindow` under Avalonia.Headless (ADR-0150), on a real core with a
real ROM loaded, and asserts what P8 promises the evaluator:

- `PreviewPanel` is null until `SelectionRect` is set — the P6 trap, asserted
  rather than described;
- the context menu of the viewer's `PictureViewer` really carries one
  `ActionType.CopyToMepSheetCell` entry, `IsVisible` and `IsEnabled` both true
  on a NES CHR source;
- invoking that entry's `OnClick` (which itself re-checks both gates, so this is
  a click, not a shortcut around one) puts **one line** on the clipboard;
- the line parses as JSON with exactly `tile` + `palette` on a CHR RAM game and
  exactly `tile` + `palette` + `index` on a CHR ROM one, `tile` 32 uppercase hex
  and `palette` 8, and equals `MepSheetCell.Format(...)` character for
  character.

**The clipboard write is asserted, not assumed.** That needed one hack, and it
is the only one in the file: Avalonia.Headless installs no application lifetime
and Avalonia refuses `Application.ApplicationLifetime = …` after startup, so
the shipped `ApplicationHelper.GetMainWindow()` would answer null, the copy
would be a silent no-op, and the test could not tell that apart from a refusal.
The test writes `Application`'s private lifetime field by reflection to install
a desktop lifetime whose `MainWindow` is the viewer window, and skips with an
explicit reason if a future Avalonia makes that impossible. What is asserted is
therefore the text the *shipped* `HdPackCopyHelper.CopyAsMepSheetCell` really
puts on a clipboard, not a re-implementation of it.

The test walks the tilemap 8 px at a time until one tile answers, because known
trap 4 is real: `IsEnabled` checks only the memory type, so a click can be a
silent no-op. Each attempt clears the clipboard first, so a text read back is
never a stale one.

## P9–P14 — the replay script

`python3 scripts/replay_f122_panel.py --game both`, exit 0. Per game it copies
the work copy, appends the cell P10 describes, grows the canvas where P11 says
to, paints the 32×32 magenta square at P12's pixel, runs `mep_build.py build`,
reads the pasted key back out of `hires.txt`, runs `mep_lint.py`, installs the
pack to `<rom dir>/mep/`, reopens the ROM at the reference frame and counts
magenta pixels in the screenshot. `<rom dir>/mep/` is removed again when the run
finishes; it refuses to start if that folder is not free.

### Standing in for P7's right-click

A machine cannot click a tile on screen, and an invented key proves nothing: it
may simply not be drawn at the frame the assertion looks at. So the key is
**measured**. A probe pass paints the first 8×8 quadrant of every `metatiles`
cell with a colour that encodes the cell index, plays the same route to the same
frame, and reads the screenshot back; every probe colour found names a cell the
screen really draws. The largest one wins and its `tiles[0]` is what gets
pasted. Finding no probe colour at all is a hard failure with a stated reason,
never a fallback — see the first finding below for why that gate exists.

## Findings the replay produced

None of these is fixed here. F12.2 is shipped on `main` and this task does not
touch it.

**1. A captured `<background>` silently defeats P14, and the panel's own P4
walks the evaluator straight into one.** P4 says *"play to a screen showing a
shape you want to repaint — a bush or rock on Zelda's first overworld screen"*.
Every static overworld screen the Zelda route visits was captured by the
recorder as a whole-screen `<background>` (the pack carries 15; Contra carries
6). When one matches, the emulator draws that PNG and **every `<tile>` rule is
ignored**. Measured directly: with all 15 Zelda backgrounds flooded cyan and
both `metatiles.png` and `misc.png` flooded magenta, six sampled points of the
route (50/60/75/90/105/120 s) rendered 969 072–980 368 cyan pixels and **zero**
magenta. The build is green, `hires.txt` carries the key at the painted crop,
lint is clean — and nothing changes on screen. There is no message anywhere
saying why. The replay works around it by asserting on a frame the recording did
not capture (Zelda 47 s, Contra 22 s) and by gating on the probe, but the human
panel has no such gate: an evaluator who paints the bush on Zelda's first screen
will do everything right and see nothing.

**2. `mep_build.py build` is not idempotent on these packs.** A second `build`
over the same folder exits non-zero with 32 `#253` errors of the form *"painted
tile … lost to sheets/sprXXX.png — the repaint cannot affect that key at run
time"*. Reproduced on a pristine copy of `~/f12.2-panel/zelda`: first build rc 0,
second build rc 1. The cause is that the first build rewrites 12 sprite sheets in
place (`spr000/005/006/008/009/011/012/016/017/018/024.png` and `sprites.png`,
the flip-unbake pass), and its own output then reads as *painted* on the next
run. P13 is a single command, so a first-time evaluator will not hit it — but
anyone who fixes a typo in `misc.json` and builds again will, and the error text
points at sprite sheets they never touched. The replay avoids it by building
every pack exactly once, from a fresh copy.

**3. One stale coordinate in the panel script.** Its *"Why criterion 5 is
written against `build`"* section quotes Contra's round-trip as
`…,0F192908,140,276,…`; P12 and the later *"re-recorded packs"* section both say
the painted pixel is `4,276`, and the replay's own Contra line comes out at
`4,276`. The `140` is stale.

## Honest limits

- **Cold-read discoverability is unmeasured.** Criterion 1 ("the evaluator
  reaches *Copy as MEP sheet cell* without being told the menu path, under 2 min
  from pause") has no mechanical analogue. The headless test finds the action by
  `ActionType`, which is the opposite of discovering it.
- **The P15 judgement is unmeasured.** Elapsed minutes, how many times the
  evaluator looked something up, and *"whether picking a key this way beats
  typing it from a spreadsheet"* are the point of the row, and none of them is
  in this log.
- **Criterion 4 is unmeasured.** Whether `hires.txt` was opened is a fact about
  a person. The replay reads `hires.txt` on purpose, at P13, to assert the round
  trip — which is exactly what the evaluator is forbidden to do.
- **Criterion 8 is unmeasured.** *"Did the evaluator expect feedback after
  clicking?"* is an observation, recorded verbatim or not at all.
- **The replay does not click anything.** P5–P7 are exercised through the
  ViewModel and the context-menu action object, not through pointer input on a
  realized menu. A regression in the `.axaml` that made the menu unopenable, or
  in `ContextMenu_Opening`, would not be caught here.
- **The key is not the evaluator's key.** The replay pastes a key it measured as
  visible; the panel's own example keys
  (`384CC6C6C66438000000000000000000` for Zelda) are *not* what it uses. The
  Zelda example key was tried first and produced zero magenta at the reference
  frame — it is simply not drawn there.
- **The 16 px-tall sprite case is untested.** Known trap 3 (two objects, no
  comma between them) is out of scope for both the panel and this replay.
- **Two frames, not a game.** Each game is asserted at exactly one frame of one
  route. A tile that renders there says nothing about the rest of the game.
- **The headless test needs ROMs and a built core.** Without `MESEN_NES_ROMS`
  and a local `MesenCore`, it skips with an explicit reason — so on CI
  (ADR-0131) it never runs.
