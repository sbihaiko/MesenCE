## L-282110275400-000 · bug · 2026-08-26
**Pedido:** (not available)
**Diagnóstico (scout/spec):** Identified in: scripts/validate_palette_variants.py
**Por que falhamos / como evitar:** The Python harness implicitly assumed "binary exists" == "binary is up to date": ensure_capture_tool() only ran `make capture-tool` when the file was missing, never when it was stale relative to the MesenCore.dylib/sources it links. This is a class of build-artifact staleness not tracked by git (scripts/headless_record is in .gitignore, so there is no commit timestamp to compare against, only the local disk mtime). The symptom (SIGABRT from a missing dyld symbol, before any HdPackBuilder code runs) was easy to misdiagnose as a logic bug in HdPackBuilder because AC-3 only reports "process aborted during recording", without distinguishing a dynamic-loading failure from a real runtime failure. Avoid: compare the binary's mtime against the .dylib's (or simply always invoke `make capture-tool`, which is idempotent and always relinks because the target matches no file and the Makefile declares no .PHONY) instead of an existence check.
